# UI Connected Workflow For Claude

This is the handoff note for building the next UI without manual JSON editors.
The UI should be a planner cockpit that calls engine/API workflows directly.
Do not reimplement scheduling decisions in React.

## Product Rule

The engine owns:

- validation
- scheduling strategy selection
- repair scope
- WIP / firm / frozen locks
- feasible slot suggestions
- edit preview/apply
- scenario compare/publish
- diagnostics and explanations

The UI owns:

- clean forms
- stateful navigation
- Gantt rendering
- action buttons
- showing diagnostics and warnings

## Default Boot Flow

On app load:

1. `GET /health`
2. `GET /ready`
3. `GET /auth/me`
4. `GET /scheduling/strategies`
5. `GET /workspaces`
6. `GET /work-orders`
7. `GET /machines`
8. `GET /resources`
9. `GET /inventory`
10. `GET /supplies`
11. `GET /scheduling/runs`

If there is no run, show a "Create baseline plan" button, not a JSON box.

## Company And User Session

Do not ask planners to manually type `X-Organization-Id` or `X-User-Id`.
The UI should create one explicit session context and then let the API client
attach the headers centrally.

The product UI should expose this as a real `/login` experience. Do not hide
the company/user selector inside a data/system screen only. If no active
context is stored locally, redirect planner pages to `/login`.

Use:

```http
POST /auth/login
GET /auth/me
POST /auth/switch-organization
POST /auth/logout
```

MVP login payload:

```json
{
  "user_id": "user-1",
  "organization_id": "org-demo"
}
```

The response returns:

- `user`
- `active_organization`
- `active_membership`
- `memberships`
- `permissions`

Store only the selected context locally, then attach:

- `X-Organization-Id = active_organization.id`
- `X-User-Id = user.id`

`Organization` is the company/tenant boundary. `Workspace` is a planning
container inside that company. Do not create a second frontend-only company
model.

Roles exposed by the MVP:

- `owner`
- `admin`
- `planner`
- `viewer`
- `integrator`

The UI should render or hide APS actions using `permissions`, but the API also
enforces permissions for scheduling, planner edits and scenario publishing when
a scoped user is active.

## Strategy Capability Catalog

The UI must not hardcode scheduling strategies. Load:

```http
GET /scheduling/strategies
```

Use only strategies where:

- `available = true`
- `ui_groups` contains the screen purpose, for example `baseline` or `compare`

For the baseline form, default to the strategy with
`default_for_baseline = true`. This should normally be `auto`, which is the
engine decision layer and not a separate solver. `auto` lets the engine choose
the production-safe solver path from current data, disruption state, and
planning policy.

If a strategy is unavailable, do not show it in normal planner dropdowns.
Advanced/debug screens may display it with `availability_reason`. For example,
`cpsat` is marked unavailable when OR-Tools is not installed, so the UI should
not let a planner launch it and then show a generic Internal Server Error.

Fields to surface in UI help text:

- `label`
- `description`
- `maturity`
- `planning_mode`
- `optimization_mode`
- `notes`

Production-safe rule: baseline forms should generally expose only strategies in
the `baseline` group. Compare or diagnostic screens can expose `compare` and
`advanced` groups separately.

## Baseline Plan Button

Button label: `Create baseline plan`

Call:

```http
POST /scheduling/run
```

Payload generated by UI state:

```json
{
  "horizon_start": "2026-01-05T00:00:00",
  "horizon_days": 7,
  "strategy": "auto",
  "heuristic": "edd",
  "persist": true,
  "workspace_id": "default",
  "scenario_name": "Baseline",
  "lifecycle_status": "draft"
}
```

After success, store `schedule_id`, then load:

- `GET /scheduling/runs/{schedule_id}/dashboard`
- `GET /scheduling/runs/{schedule_id}/readiness`
- `GET /scheduling/runs/{schedule_id}/gantt`

## Gantt Data Contract

Use `GET /scheduling/runs/{schedule_id}/gantt`.

Render from:

- `machine_lanes`
- `work_order_lanes`
- `items`

Each item includes enough to render a rich bar:

- identity: `operation_id`, `work_order_id`, names
- timing: `setup_start`, `start`, `end`, `segments`
- machine: `machine_id`, `machine_name`, `eligible_machine_ids`
- planning: `execution_status`, `planning_lock`, `planning_zone`
- interaction: `movable`, `override_required`, `required_override_action`
- override policy: `override_policy.move_policy`,
  `override_policy.required_action`, `override_policy.review_required`,
  `override_policy.publish_review_required`
- source state: `actual_start`, `actual_machine_id`, `actual_end`,
  `actual_consumed_minutes`, `remaining_duration_minutes`,
  `planned_remaining_minutes`, `wip_repair_mode`
- fences: `firm_until`, `frozen_until`
- comparison: `baseline_machine_id`, `baseline_start`, `changed_from_baseline`
- alerts: `warnings`, `is_late`, `is_critical`, `is_preempted`

Use these fields directly to enable/disable drag/drop.
The canonical decision field is `override_policy.move_policy`:

- `allowed`: normal preview/apply flow.
- `review_required`: slushy/soft-locked; allow preview/apply, but show
  stability review before publish.
- `override_required`: firm/manual-pinned; generate or request
  `unfreeze_operation` before move.
- `blocked`: WIP/completed/hard-frozen; do not drag.

If an item is WIP/completed and has `actual_machine_id`, treat that as the
shop-floor machine source; do not ask the user to re-enter it in JSON.
For partial WIP bars, use `segments[].segment_type`: show `actual_consumed` as
history. A run created by the engine's WIP repair split returns
`remaining_planned` for the solved remaining segment; older/manual schedules may
still return `remaining_frozen`.
When `wip_repair_mode = actual_consumed_frozen_remaining_schedulable`, render
the canonical operation as one bar with two visual states and keep all actions
targeting the canonical `operation_id`, never the synthetic
`__actual_consumed` id from diagnostics.

## No Manual JSON For Planner Actions

Replace JSON textareas with specific UI actions.

### Move Operation

User flow:

1. Planner clicks/drag an operation.
2. UI calls feasible slots.
3. UI shows slot cards or highlighted Gantt slots.
4. Planner selects one.
5. UI previews the edit.
6. Planner applies the candidate if acceptable.

Calls:

```http
GET /scheduling/runs/{schedule_id}/operations/{operation_id}/feasible-slots
```

Then:

```http
POST /scheduling/runs/{schedule_id}/edits/preview
```

Generated payload:

```json
{
  "strategy": "auto",
  "reschedule_mode": "repair_local",
  "scenario_name": "Move preview",
  "lifecycle_status": "simulation",
  "edits": [
    {
      "edit_type": "move_operation",
      "operation_id": "OP-1",
      "machine_id": "M2",
      "start": "2026-01-05T10:00:00",
      "end": "2026-01-05T11:00:00"
    }
  ]
}
```

Then if accepted:

```http
POST /scheduling/runs/{schedule_id}/edits/apply
```

Same payload, but use a real scenario name like `Planner candidate`.

### Freeze / Unfreeze

Use the Gantt item fields:

- if `planning_lock = firm` and `override_required = true`, show `Unfreeze`.
- if `planning_lock = started_frozen` or `completed_frozen`, do not show normal
  drag/drop. Show WIP/read-only status.
- if `frozen_until` blocks the move, show "Hard frozen until ..." and no
  override button.

Generated preview edit:

```json
{
  "edits": [
    {
      "edit_type": "unfreeze_operation",
      "operation_id": "OP-1"
    }
  ],
  "reschedule_mode": "repair_local",
  "strategy": "auto"
}
```

### Change Priority

Use a small select/dropdown, not JSON.

Payload:

```json
{
  "edits": [
    {
      "edit_type": "change_priority",
      "work_order_id": "WO-1",
      "priority": 1
    }
  ],
  "reschedule_mode": "repair_local",
  "strategy": "auto"
}
```

### Gantt Planner Action Buttons

The operation inspector should expose planner actions from
`items[].editable_actions`; do not show actions that the engine omitted.

Supported no-JSON buttons/forms:

- `preview_move`: call feasible slots, then preview/apply `move_operation`.
- `force_machine`: machine select from `eligible_machine_ids`, preview/apply
  `move_operation` with only `machine_id`.
- `freeze_operation`: preview/apply a firm candidate using the baseline
  placement.
- `unfreeze_operation`: release manual/firm locks before another move.
- `standby_operation`: remove the operation from the candidate plan.
- `change_priority`: work-order priority select.
- `override_due_date`: work-order due date picker.
- `exclude_work_order`: remove the whole work order from the candidate plan.

All of these must call:

```http
POST /scheduling/runs/{schedule_id}/edits/preview
```

Then, if accepted:

```http
POST /scheduling/runs/{schedule_id}/edits/apply
```

After apply, store the returned `candidate_schedule_id` and route the planner
to Scenarios for compare/publish. Never mutate the baseline schedule directly.

### Add Overtime

Use a form:

- target machine or calendar
- start
- end

Send through edit preview/apply as planner action when available, or directly
through `/scheduling/run` `planner_actions` for the first MVP.

## Candidate Review Flow

After `edits/apply`, store `candidate_schedule_id`.

Load:

- candidate Gantt with baseline:
  `GET /scheduling/runs/{candidate_schedule_id}/gantt?baseline_schedule_id={baseline_id}`
- compare:
  `POST /scheduling/scenarios/compare`
- readiness:
  `GET /scheduling/runs/{candidate_schedule_id}/readiness`

Readiness diagnostics expose `diagnostics.planning_policy_summary` with direct
UI counts: `partial_wip_repair_count`, `firm_fence_count`,
`hard_frozen_count`, `manual_pinned_count`, and `slushy_review_count`.
Use `recommended_review_actions` to decide which review cards/buttons to show.

Publish only after review:

```http
POST /scheduling/scenarios/{candidate_schedule_id}/publish
```

Payload:

```json
{
  "baseline_schedule_id": "run-baseline",
  "scenario_name": "Approved plan",
  "allow_review": true
}
```

UI behavior expected for this flow:

- Keep `baselineScheduleId` and `candidateScheduleId` separate in app state.
- Never allow the same run to be both baseline and candidate.
- Prefer the latest `published` feasible run as the default baseline.
- Prefer the latest draft/candidate/simulation feasible run that differs from
  the baseline as the default candidate.
- Read scenario comparison fields exactly from `comparisons[].metric_delta`,
  `comparisons[].stability_report`, `comparisons[].publish_status`, and
  `comparisons[].recommendation`.
- After publish succeeds, promote the returned `schedule_id` to the active
  baseline and clear the candidate selection.
- Use `GET /scheduling/runs/{candidate_id}/gantt?baseline_schedule_id={baseline_id}`
  for candidate Gantt comparison rendering.

Do not rebuild scenario scoring or publishability in React. The API owns
`recommended_schedule_id`, `publishable_schedule_ids`, `publish_status`, and
the recommendation text. The UI only displays and gates buttons from those
fields.

## Runtime State Recovery

The UI stores active `baselineScheduleId` and `candidateScheduleId` in browser
state. Those IDs can become stale after a Docker reseed, DB reset, schedule
delete, or switching tenant.

Required behavior:

- Periodically reconcile active IDs with `GET /scheduling/runs`.
- If there are no persisted runs, clear both active IDs.
- If the active baseline no longer exists, select a valid baseline or clear it.
- If the active candidate equals the baseline or no longer exists, clear or
  replace it with a valid candidate.
- If `GET /dashboard`, `GET /readiness` or `GET /gantt` returns 404 for the
  active schedule, clear that active ID instead of leaving the page stuck.
- Disable links/buttons that require a baseline or candidate rather than using
  clickable links with only `aria-disabled`.

Gantt planner actions must also have explicit busy states:

- `fetching_slots`
- `previewing`
- `preview`
- `applying`
- `applied`

Do not leave the inspector in `idle` while a preview/apply request is in flight;
that allows double submissions and confusing candidate creation.

## Recommended UI Pages

- `System`: health, ready, seed status, API warnings
- `Data`: work orders, machines, resources, inventory, supplies
- `Scheduling`: baseline run, dashboard, readiness, run history
- `Gantt`: machine lanes, operation bars, feasible slots, edit preview/apply
- `Scenarios`: compare candidates and publish
- `Exceptions`: planner exceptions, material blockers, resource conflicts

## Implementation Notes

- Create typed API client functions instead of calling `fetch` inline in every
  component.
- Keep schedule IDs in app state.
- Keep selected baseline and selected candidate separate.
- Avoid manual JSON except in a developer/debug drawer.
- Use API diagnostics to populate user-facing messages.
- If the UI needs a missing field, add it to the API read model instead of
  deriving scheduling logic in React.

## Smoke Before UI Work

Run this before UI integration:

```powershell
docker compose -f docker/docker-compose.yml run --rm --build migrate
docker compose -f docker/docker-compose.yml run --rm --build -e SEED_DATASET=industrial -e SEED_RESET=true seed
docker compose -f docker/docker-compose.yml up --build -d api
docker compose -f docker/docker-compose.yml run --rm --build smoke
```

Expected smoke output includes `candidate_schedule_id`, `comparison_count = 1`
and `publish_status`. If those fields are missing, the UI branch is connected
only to read models and not to the complete planner workflow yet.
