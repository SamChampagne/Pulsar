## 2. Engine cheatsheet (how it actually runs)

**Architecture — hexagonal, strict dependency rule:**
```
api / cli  →  application  →  domain
                   ↑
           infrastructure implements application.ports
```
`domain/` never imports anything else. Use cases take `*.ports` repositories
in `__init__`; SQL adapters in `infrastructure/db/repositories/`; in-memory
twins in `infrastructure/in_memory/repositories.py` (used by tests + CLI).

**Strategy registry (`domain/scheduling/strategy.py`):**
- `SchedulerStrategy` Protocol; strategies register a factory so heavy deps
  (CP-SAT) stay out of import time.
- Resolved by `resolve_strategy(name)`. Same input → same output for all
  strategies (deterministic tiebreak by machine_id then operation id).
- Each strategy returns `StrategyResult(schedule, objective_value,
  wall_time_ms, solver_status, diagnostics)`.
- Strategies stateless; reusable across runs.

**Available strategies:**
| Name | Profile | When to use |
|---|---|---|
| `greedy` | online dispatch, real-time safe | default; disruption replan; rolling horizon |
| `backward` | JIT, due-date driven | tight-due-date scenarios; CTP |
| `cpsat` | exact, OR-Tools dep | what-if, small to medium horizons |
| `infinite` | rough-cut, no capacity | CTP first pass, demand modelling |
| `sa` / `tabu` / `ga` / `lns` / `multi` | metaheuristic | tactical optimisation; not the disruption path |

**Core entities (`domain/entities/`):** `WorkOrder`, `Operation` (with
`RoutingAlternative` list — machine-specific duration/setup/resource), `Machine`,
`WorkingCalendar`, `Schedule`, `Resource` (secondary, cumulative capacity),
`Material`. Value objects in `domain/value_objects/` — `Duration`, `TimeWindow`,
`Shift`, `Priority`.

**Constraints honoured by the engine (verified):**
- Finite capacity, no overlap on machines, cumulative on secondary resources
- Setup matrix lookup (family-aware, machine-specific) — `setup_lookup.py`
- Calendars + shifts + holidays + maintenance windows — `calendar_resolver.py`
- Cross-WO dependencies (FS / SS, lag, max_wait) — `dependency_links.py`
- Frozen assignments — `frozen.py`
- Material reservation — `material_ledger.py` (no BOM yet)

**Multi-objective scoring (`domain/scheduling/objective.py`):** 7 weighted
components — makespan, total_tardiness, weighted_tardiness, setup_cost,
idle_penalty, start_shift_penalty, machine_change_penalty.

**Post-hoc analysis (`domain/scheduling/analysis.py`, 415 lines):**
critical path, bottleneck, per-machine utilisation, work-order flow times,
Gantt export. Pure functions, no DB access. Used by `get_schedule_dashboard`,
`get_schedule_gantt`, `run_disruption`, `result_summary`, `run_scheduling`.

**API surface (`api/routes/scheduling.py`):**
- `POST /scheduling/runs` — run a strategy on a snapshot
- `GET /scheduling/runs` — list (org-scoped)
- `GET /scheduling/runs/{id}` — read one
- `DELETE /scheduling/runs/{id}` — tenant-checked (J7)
- `PATCH /scheduling/runs/{id}/context` — tenant-checked (J7)
- `POST /scheduling/runs/{id}/replay` — **IDOR open, see P0.1**
- `GET /scheduling/runs/{id}/dashboard` `/capacity` `/readiness` `/gantt`
  `/risk` `/operations/{op}/feasible-slots` — use-case-layer scoped only

**Tenant pattern (`api/tenant.py` + `infrastructure/scoping.py`):**
- `TenantContext(organization_id, user_id, workspace_id?, roles)` resolved
  from `X-Organization-Id` / `X-User-Id` headers via Membership lookup.
- `ScopedRepositoryMixin` filters every query by `organization_id` —
  prevents leaks at repo layer.
- `_ensure_schedule_in_tenant_scope(id, metadata, tenant)` in
  `routes/scheduling.py:787` returns 404 (never confirms existence) when
  the schedule belongs to another org/workspace. **This is the helper P0.1
  must apply to the 7 still-unscoped routes.**

### P0.2 — Transaction safety + binding races on import ✅ DONE

**Mini-spec.**
- Wrap `ImportPlanningSnapshot.execute()` (`application/use_cases/import_planning_snapshot.py`)
  in a DB transaction. Today it does `repo.add(...)` per entity inside a
  loop (line 258-265). If `machines.add()` fails after `calendars.add()`,
  calendars stay orphaned.
- Solution: the use case must accept a `Session` (or work through a UoW port)
  so the route can `try ... session.commit() except ... session.rollback()`.
  Look at how `delete_run` / `update_run_context` already do this — they
  receive `session: Session = Depends(get_db_session)` and call
  `session.commit()` after the use case succeeds.
- `IntegrationBindingRepository.save()` (both SQL + in-memory) must do an
  atomic upsert. Today: two concurrent flows both miss the lookup, both
  call `save()`, both create duplicate bindings. Fix: PostgreSQL
  `ON CONFLICT (entity_type, source_system, external_ref) DO UPDATE SET
  internal_id = EXCLUDED.internal_id` (the table has a unique index already
  — verify in `infrastructure/db/models/integration_binding_model.py`).

**Files.**
- `application/use_cases/import_planning_snapshot.py`
- `application/ports/integration_binding_repository.py` (no signature change
  — same `save()`, just stronger guarantee)
- `infrastructure/db/repositories/integration_binding_repository.py`
- `infrastructure/in_memory/repositories.py`
- `api/routes/integration.py` (wherever `ImportPlanningSnapshot.execute` is
  called from the route)
- `tests/unit/use_cases/test_import_planning_snapshot.py` — new test:
  inject a repo that raises on the 3rd entity, assert the first two are
  rolled back.
- `tests/unit/use_cases/test_binding_concurrency.py` — new file: hammer
  `save()` with the same external_ref from two threads, assert single row.

**Done definition.**
- Mid-import failure leaves DB in clean (pre-import) state.
- Two concurrent flows with same external_ref produce one binding, not two.
- All existing tests green.

**Outcome.** The transaction wrapper turned out to already exist —
`SessionFactory.session()` in `infrastructure/db/session.py:39-50` is a
context manager that commits on clean exit and rolls back on any
exception. P1 audit overstated this gap. Pinned the guarantee with 3
regression tests in `test_session_factory_transaction.py` so a refactor
can't silently downgrade it.

The real fix was the binding upsert: `SqlIntegrationBindingRepository.save()`
did `SELECT` then conditional `INSERT`/`UPDATE` in two SQL statements —
two concurrent imports could both miss the `SELECT`, both `INSERT`,
loser crashed on `uq_integration_binding_key` (HTTP 500). Replaced with
PostgreSQL `INSERT ... ON CONFLICT DO UPDATE SET updated_at` (preserves
the existing `internal_id`) + `RETURNING`. The port signature evolved
from `save(b) -> None` to `save(b) -> IntegrationBinding`: the return
is the binding actually persisted, so the caller can detect a lost race
when `saved.internal_id != b.internal_id`. `ImportPlanningSnapshot._resolve_internal_id`
now re-converges on the winner's id in that case (no downstream fork).

In-memory twin mirrors the semantics (first-writer-wins, no overwrite).
6 new tests in `test_integration_binding_first_writer_wins.py` cover
basic save, idempotency on duplicate key, lost-race detection from
return value, key isolation across entity_type / external_ref, and an
end-to-end use-case re-convergence test. 1053 / 1053 unit tests green.

### P0.3 — Flow error recovery + 429 backoff

Split into two slices: P0.3a (Odoo client backoff, no migration, fast)
and P0.3b (per-block retry / skip + UI, needs DB migration).

#### P0.3a — Odoo client 429 backoff ✅ DONE

**Outcome.** `OdooClient._post()` now retries on HTTP 429 with
exponential backoff (1 s, 2 s, 4 s — max 7 s of total wait across 3
retries). Non-429 errors propagate immediately so the caller can
decide whether to skip or abort. A short rate-limit burst from a busy
ERP no longer kills the whole flow. Constructor takes a `sleep`
callable injected for tests; 6 new tests in `test_odoo_client.py`
cover: succeed after 1 / 3 retries, give up after 3, no sleep on
immediate success, non-429 errors do NOT trigger retry, push path
(`write`) shares the same backoff via `_post`.

#### P0.3b — Per-record breakdown on push blocks ✅ DONE

**Audit correction.** The original P0.3b mini-spec asked for retry +
skip + per-record errors. Auditing the code more carefully showed:

- **retry_count is already done.** `_run_block_with_retry`
  (`integration_flows.py:4369`) reads `retry_max_attempts` +
  `retry_backoff_seconds` from each block's JSON config and applies
  linear backoff. 4 tests in `test_flow_block_retry.py` cover the
  happy path, default (1 attempt), exhaustion, and sleep timing. The
  V1.1 phase 7 work already shipped this — the audit missed it.
- **skip_on_error is also already done**, but as **typed `error`
  edges** in the DAG rather than a boolean field. `_block_has_error_edge`
  + the edge_type === "error" branch in `_activated_edge_types_for_block`
  let a planner wire `block_X --error--> block_Y` so failures route to
  a recovery path. 4 tests in `test_flow_error_edges.py` exercise this.

That left **per-record breakdown on push blocks** as the real gap.
Before this slice, `odoo_push_schedule` looped writes inside a single
`try/except`: on the first failure it raised "Odoo push failed:
<opaque>" and the planner had no idea whether the 5 writes BEFORE the
crash had already landed in Odoo. That's the worst kind of
all-or-nothing — half-pushed data in the ERP with no audit.

**Outcome.** The push loop now collects per-record results
(`{model, id, status, error?}`) and only raises after every write has
been attempted. When any record fails, the ValidationError message
gives the planner an actionable breakdown:

  "Odoo push partially failed: 5 OK, 2 failed — mrp.production 42:
  date_start invalid; mrp.workorder 99: not found (+0 more)"

On the success path the output payload still includes
`per_record_results: list[...]`, so the audit/journal records exactly
which Odoo IDs were touched on every run. Three tests replace the
old "first failure aborts" assertion:

- All 3 writes fail → message reports "0 OK, 3 failed" with first
  3 causes inline.
- 2 OK / 1 failed (realistic mid-loop ERP error) → message identifies
  the failing model + id + cause.
- All OK → success payload exposes per_record_results array with the
  3 entries (1 production + 2 workorders) and status "written".

1061 / 1061 unit tests green.

## P1 — controlled pilot (week 4-5)

### P1.1 — Pre-flight readiness check before flow run ✅ DONE

`POST /integration/flows/{id}/run` now calls `evaluate_readiness`
before handing the flow to the engine, refusing with HTTP 422 +
actionable blocker list when a runtime-fatal issue is detected. The
gate is intentionally narrow: only codes that the engine cannot
recover from block the run.

Allowlist (truly runtime-fatal):
- `connector_*` (registry_unavailable, missing, invalid, disabled,
  workspace_mismatch, type_mismatch)
- `credential_*` (registry_unavailable, missing, invalid, disabled,
  workspace_mismatch)
- `block_id_missing`, `block_id_duplicate`, `block_type_unsupported`
- `block_config_invalid` (e.g. call_connector_api without connector_id)

Pass-through (NOT blockers — runtime handles them):
- `flow_name_missing`, `flow_source_system_missing`, `flow_disabled`
  (warning, not blocker anyway)
- `flow_blocks_missing` (engine raises its own ValidationError)
- `database_columns_unknown`, `database_mapping_needs_preview`,
  `database_match_columns_suggested` (the database block surfaces these
  as preview data; gating them would break legitimate sandbox runs)
- `sftp_*` warnings, direct HTTP partial configs

4 dedicated tests in `test_flow_run_preflight_readiness.py`:
- connector_missing (a deleted connector) → 422, engine never invoked
- connector_id absent from block config → 422 via `block_config_invalid`
- happy path → 200, engine invoked exactly once
- `is_enabled=False` warning → passes pre-flight (canonical 409 path
  belongs to the engine, not pre-flight)

Updated 5 existing integration HTTP tests to expect 2 schema fetches
on the database write path (pre-flight + write). A future caching pass
can collapse to 1.

## P2 — daily-usable planner UX (week 6-7)

- **P2.1 Undo/Redo global** ✅ DONE for the candidate editing path.

  Surprise from the audit: AppState's `WorkingScenarioState` already
  recorded each candidate scheduleId after every edit (via
  `appendWorkingEdit`). The undo stack was sitting there unused —
  only the journal display rendered it. Walking the list back
  produces a free undo without any backend mutation: every
  intermediate candidate is already persisted, so undo / redo are
  pure view-pointer moves.

  Shipped:
  - `AppState` grows `undoCandidateEdit()` / `redoCandidateEdit()`,
    `canUndo` / `canRedo` derived flags, and a `redoStack` field on
    `WorkingScenarioState` for parked-undone edits.
  - `appendWorkingEdit` clears `redoStack` when a new edit lands —
    standard "divergent branch wipes the redo path" semantics from
    every code editor.
  - History capped at 12 entries on both sides (matches the existing
    `.slice(-12)` policy on `edits`).
  - PlanningWorkbench renders two new ghost buttons next to "Discard
    candidate": Undo / Redo with Undo2 / Redo2 lucide icons and
    tooltips spelling out the keyboard shortcuts + the "backend
    never mutates" semantics.
  - Global keyboard handler: Ctrl+Z = undo, Ctrl+Shift+Z and Ctrl+Y

  wraps `wallClock.msToNaiveIso` so display + edit share one source of
  truth.

- **P3.2 Session revocation** ✅ DONE.

  POST /auth/logout was a no-op stub: the v1 HMAC-signed bearer kept
  working until its 12-hour ``exp`` claim even after the planner
  "logged out". That's a real security gap on a shared planning
  workstation where someone walking away from the screen expects
  the next user (or a stolen tab) to be locked out immediately.

  Now persistent: SHA-256 hashes of revoked tokens land in a new
  ``revoked_auth_tokens`` table (Alembic 20260518_31). The tenant
  resolver consults the store after signature/expiry verification
  (cheap crypto gate first, then SQL round-trip), and /auth/logout
  hashes the caller's bearer + inserts the hash with the token's
  ``exp`` mirrored so a periodic purge can drop entries that would
  already fail at the cryptographic gate.

  Design choices, all pinned by tests:
  - **Fail-open on revocation store outage**: a transient DB blip
    must not mass-logout the entire plant. The signature gate keeps
    the bearer working for up to 12h of eventual-consistency rather
    than fail-closed (worse operationally).
  - **Idempotent on double-click**: ON CONFLICT DO NOTHING on
    Postgres, setdefault on in-memory. A logout button must always
    be safe to click.
  - **Tolerant on malformed/missing bearer**: logout with no header
    or a garbled token returns 200, leaves the store untouched.
    The bearer was already useless — no security gain from being
    strict, and 401 on a logout click is a dead-end UX.
  - **Hash-keyed, not user-keyed**: revoking token A leaves token B
    valid even for the same user, so admin-initiated revocation
    of one stolen tab doesn't accidentally log out an entire org.

  10 new tests across HTTP + repository contract layers. Opportunistic
  purge runs on every logout to keep the table bounded without a
  separate janitor task.

- **P3.2b Admin-initiated session revocation** ✅ DONE.

  P3.2 only covered self-logout (a planner clicking "log out" on
  their own bearer). Operators still couldn't kick a compromised
  account off the floor: a stolen laptop, an offboarded employee,
  or a shared workstation left unlocked stayed authenticated until
  the 12 h ``exp`` claim regardless of any admin action.

  The hash-keyed ``revoked_auth_tokens`` table from P3.2 is the
  WRONG shape for mass revocation — we don't store the user's
  outstanding token hashes, so we can't enumerate them at admin-
  click time. This slice adds a parallel mechanism, keyed by user:

  - New port ``UserSessionRevocationRepository`` with a single
    ``revoked_before_iat`` cutoff per user. Monotone (a later
    cutoff replaces an earlier one; an earlier cutoff is a no-op);
    default-allow on unknown users.
  - New SQL model ``user_session_revocations`` (Alembic 20260522_32):
    one row per user, ``user_id`` PK, indexed on
    ``revoked_before_iat`` for the purge query. Postgres adapter
    uses ``ON CONFLICT (user_id) DO UPDATE ... WHERE new_iat > old``
    so a regressing cutoff is dropped at the database layer.
  - In-memory twin for tests / CLI.
  - ``get_tenant_context`` consults the store AFTER the
    signature/expiry gate AND the hash-keyed gate: if
    ``claims.issued_at < user_revocation_epoch``, return 401 with
    ``reason: revoked_by_admin``. Same fail-open semantics as the
    hash gate — a DB blip on this store must not mass-logout the
    plant.
  - New route ``POST /accounts/users/{id}/revoke-sessions``:
    ``manage_accounts`` permission; cross-org target → 404 (same
    shape as "user not found", no enumeration leak); records an
    ``auth.sessions_revoked`` audit event with target_user_id in
    ``details``. Opportunistic purge call mirrors /auth/logout.

  Distinct reason codes (``revoked`` for hash-keyed self-logout,
  ``revoked_by_admin`` for the epoch path) let incident-response
  log queries distinguish "the user logged out" from "an operator
  kicked them off". The user can still sign in immediately after a
  revoke and gets a fresh working bearer — only the OLD bearers
  are blocked.

  12 new tests:
  - Route (7): planner role gets 403; cross-org target gets 404
    with no audit-event leak in the victim's log; unknown user
    same 404; happy path persists the cutoff + emits the audit
    event; pre-revoke bearer fails the next /auth/me with
    ``revoked_by_admin``; a fresh post-revoke login still works;
    double-click is monotone and 200/200, never 500.
  - Repository (5): default-allow on unknown user; cutoff is
    persisted; double-click takes latest cutoff; out-of-order
    earlier cutoff is ignored; purge drops only cutoffs older
    than ``auth_session_ttl_hours``.

  1108 / 1108 unit tests green (was 1096 before this slice).

## 4. Branch hygiene

- `claude/analyse-avancement-projet` is the V1.2 hardening branch. Each P0
  slice = 1 commit. Push after each, open PR when P0 closes.
- Don't merge to `dev` until P0 is fully green + 1 day of soak on the
  branch.
